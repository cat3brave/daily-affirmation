# よいアプリの品質基準と検証方針 — daily-affirmation

作成日: 2026-11-20 / v1.0

## 定義と目的

よいスマホアプリとは、利用者が達成したい目的を、少ない負担で、安全・快適・確実に実現でき、利用後に価値を感じられるアプリである。ここでは `daily-affirmation`（スマホ向けPWA、セルフケア支援）への適用に特化する。ネイティブAndroid/iOSアプリの審査基準をそのまま満たしたと見なしてはいけない。

**最重要成果**: 「利用者が、自分のペースで小さなセルフケアを実行できる」。ユーザーをアプリに長く滞在させることや、毎日記録させること自体は目標にしない。

### プロダクト固有の禁止・慎重項目

- 記録を休んだ日を罰したり、連続記録・強迫的な再訪を誘導したりしない。
- 否定的な自己評価、罪悪感、恐怖、過度なポジティブ強制による継続利用を促さない。
- セルフケアの提案を医療診断・治療の保証・緊急対応の代替として提示しない。
- 個人の内省・日記・AI入力などの機微な内容を、許可なく送信・ログ出力・分析収集しない。
- AIの新機能は、外部送信、費用、失敗時の代替動作、誤回答の影響を先に確認する。
- 入力しない、完了しない、閉じる、戻る、休む、という選択を尊重する。

## 10の評価軸

詳細な質問・重み・例は `rubric.json` を参照。重みの合計は100だが、これはチームが優先順位を話し合うための暫定的な仮定であり、検証済みの尺度ではない。全項目を単一スコアだけで最適化しない。

| 項目 | 重み | 主要な観察・検証例 |
| --- | ---: | --- |
| 有用性 | 18 | 主要タスクの完了率、利用後の有用感 |
| 直感性 | 11 | 初回利用者が迷わず始められるか |
| 操作性 | 11 | タップ回数、戻る・取消・再試行、下書き維持 |
| 視認性 | 9 | 320px幅、文字拡大、コントラスト、情報の優先順位 |
| 快適性 | 9 | 速度・待機・動きの少なさ、LCP/INP/CLS（実測時） |
| 信頼性 | 12 | 保存の成功・失敗、回帰テスト、負荷に対する安定 |
| 安全性 | 10 | 認証/認可、RLS、API送信、データ分離と透明性 |
| アクセシビリティ | 10 | WCAG 2.2 AA、キーボード、読上げ、タップ対象 |
| 情緒的価値 | 6 | 心理的圧迫の少なさ、言葉遣い、自主性 |
| 持続可能性 | 4 | 依存関係、保守のしやすさ、AI利用コスト |

## 品質評価の証拠の強さ

1. 実際の利用者によるタスク観察・フィードバック（有用性・直感性・情緒的価値）。
2. 同条件での前後比較、実測の動作記録、E2E、アクセシビリティ検査（観測可能な振る舞い）。
3. 単体テスト、静的解析、コードと設計のレビュー（個別の正しさ・リスク）。
4. AIの画面印象や「使いやすそう」という自己評価（仮説作成のみ）。

利用者評価と自動テストは異なる問いに答える。安全性やDB認可では自動・隔離環境による技術的検証を優先し、人の印象で代替しない。

**観測できない項目は `score: null` とし、証拠がないのに4/4を付けない。**

## 実際の確認条件（基準と内部目標を区別する）

### UI・アクセシビリティ

- W3C WCAG 2.2 AAを参照し、通常テキストのコントラスト4.5:1、大きなテキスト3:1、200%文字拡大、キーボード操作、フォーカス、reflowを確認する（適用上の例外に注意）。
- WCAG 2.2 AAのターゲットサイズ最低条件は原則24×24 CSS pxで例外あり。タッチ操作の**本アプリ独自の設計目標**は可能な限り44×44 CSS px以上（Androidネイティブの48dpと混同しない）。
- 320 CSS px幅と大きな文字サイズで横スクロール・ボタン欠け・フォーカス不達がないか確認する。
- axe等の自動検査に加え、キーボード、スクリーンリーダー、視覚レビューを組み合わせる。
- 動きを減らす設定（`prefers-reduced-motion`）を尊重する。

### 性能

- Core Web VitalsはWeb向けの指標。実利用者データ（RUM）が得られる場合はモバイルの75パーセンタイルを基本とし、参考目標は LCP<=2.5秒、INP<=200ms、CLS<=0.1。
- ラボの1回の測定を実利用者全体の合格判定に転用しない。実測なしなら「未測定」と書く。
- 数字だけでなく、ユーザーがタップして結果が見えるまでの遅延、読み込み時の状況表示、失敗からの復帰を観察する。

### コアシナリオ

- ログインからダッシュボードへの遷移と認証境界。
- 「3つのよかったこと」の入力・保存・再表示・下書き復元・エラー時の挙動。
- やさしい翻訳機でAI有効/定型文代替/エラー時の振る舞い。
- アファメーションのお気に入り登録・削除、他ユーザーのデータ分離。
- お花の成長、深呼吸、戻る/閉じる、動作軽減モード。
- `/privacy`の説明内容と、実装されているデータの扱いの一致。

**これらは既存機能の評価対象例であり、このハーネスを作った時点で動作確認したという意味ではない。**

## 改善候補の優先順位

AIは改善候補ごとに以下を添える。

- 事象と再現条件: どの画面、どの操作、何が起きたか。
- 根拠と確信度: 観測事実／推論／未確認を区別。
- 影響: 有用性・操作性・安全性・アクセシビリティなど。
- 見込み効果: 利用者のどの負担を減らすか（実測前なら仮説）。
- 変更案・代替案・リスク・検証方法。
- `impact/reach/confidence/effort/risk` は各1〜3の相対指標とする。

`rubric.json` の相対値による優先順位は議論のたたき台であり、ユーザー調査を代替しない。重大な安全性・プライバシーの問題はスコアに関係なく優先して扱う。

## 必須ゲート

リリース・マージの判断前に `rubric.json` の7ゲートをすべて根拠付きで `pass` とする。失敗/未確認は完了扱いにしない。ツールが表示する `READY_FOR_HUMAN_REVIEW` はレビューを進められる状態という意味であり、マージ承認ではない。

既存 `AGENTS.md` が最優先。変更のローカル検証レベル0〜3、全量CIと `Verify`、PRのVercel・競合・レビューの確認を維持する。**ユーザーの明示的な依頼がない限りcommit、push、PR、mergeを実行しない**。

### 停止条件

- 重大なセキュリティ／認可／プライバシーの懸念が未解決。
- 変更範囲の許可を超える必要がある。
- 必須テスト失敗／失敗原因不明／環境制約で未検証。
- 現行UIの重要なタスクで回帰が確認された。
- CI/Vercel/差分レビューが未完了、競合がある。
