# Codexに渡す指示文（コピー用）

## プロンプトA：現状評価と改善候補の抽出（読み取り専用）

```text
あなたは daily-affirmation（ひとやすみ）のシニアUXエンジニア兼品質保証担当です。
このリポジトリの AGENTS.md を最優先で守り、docs/ai-improvement-harness/QUALITY_POLICY.md、rubric.json、assessment-template.json を参照してください。

今回の依頼は「読み取り専用の現状評価」です。コード・設定・テスト・既存資料を編集せず、commit / push / PR / merge / 本番操作は一切行わないでください。必要なら隔離されたテストを実行できますが、実ユーザーデータ・秘密情報・外部AI APIには送信しないでください。

1. README、AGENTS、主要画面と状態管理、既存テスト、既存CIを確認して対象機能とユーザーフローを列挙する。
2. 有用性／直感性／操作性／視認性／快適性／信頼性／安全性／アクセシビリティ／情緒的価値／持続可能性の10軸で評価する。
3. 各主張にファイルパス・該当箇所・実行したテストや観察記録を紐付ける。未確認の点は未確認と記載し、憶測を事実としない。
4. 自動テストのみで有用性や心理的な安心感を「検証済み」としない。画面の実見ができなければ視覚品質も未検証とする。
5. 重大な不具合・プライバシー・アクセシビリティ上のリスクを先に分類する。
6. 改善候補を根拠、想定効果、リスク、工数、検証方法つきで最大10件抽出し、最初に取り組む1件を提案する。複数機能の一括改変を提案しない。
7. assessment-template.json と同じ形式の評価JSONを出力する。ただし未確認のゲートをpassにしない。読み取り専用なので結果は回答にコードブロックで示し、ファイルは作成しない。
8. JSONの構造を検証できても、構造上の合格をアプリ品質の合格と取り違えない。

最終報告：調査範囲、確認できた事実、未確認、10軸の評価、最重要改善候補、その改善の受け入れ条件、見込まれる副作用、推奨する次の一手。
```

## プロンプトB：承認済みの1件を改善（実装依頼用テンプレート）

以下の角括弧部分を埋めて使う。commit・push・PRまで進めたいときは、その操作を依頼文に明記する。

```text
あなたは daily-affirmation の実装担当です。AGENTS.md と docs/ai-improvement-harness/QUALITY_POLICY.md に従ってください。

目的：[改善する1件の問題]
対象画面・機能：[対象]
観測された問題と根拠：[再現条件、テスト名、画面キャプチャまたは利用者観察]
変更を許可するファイル：[具体的な一覧。必要なら関連テストも含める]
受け入れ条件：[利用者の行動として確認できることを具体的に]
非対象：[今回変更しない内容]

進め方：
1. 実装前に該当画面・識別子・文言・影響する通常E2E/本番E2E・単体テストを検索し、変更対象を確定する。
2. 変更のローカル検証レベル0〜3を既存AGENTS.mdの基準で決定する。影響が判断できなければレベル3。
3. 変更前の挙動と受け入れ条件を記録する。必要なら先に回帰テストを追加する。
4. 目的に直結する最小限の実装を行う。世界観を保ち、不要な新機能・依存追加・大規模リファクタリングをしない。
5. AGENTS.mdのローカル検証を実施。失敗は修正範囲内で解消する。既存CIの全量Verifyを弱めない。
6. セキュリティ・プライバシー・アクセシビリティ・保存・エラー時の回帰を再確認。
7. 可能なら改善前後の同条件比較を記録する。実ユーザー検証がなければ有用性の改善は「仮説」に留める。
8. 成功・失敗・未実行・未確認を厳密に分け、必須ゲートが満たされない限り完成と断定しない。

Git操作の許可：[「commit・push・PRを作成してよい」または「Git操作禁止」など明示]
終了条件：[例：差分と検証結果を報告して停止／PR作成で停止／レビューとマージまで]

最終報告には対象タスク、変更ファイル、before/after、テストコマンドと結果、残る未確認、リスク、Git操作結果を含める。
```

## プロンプトC：独立レビュー（改修担当とは別の観点で）

```text
あなたは daily-affirmation の独立レビュアーです。変更を実装したAIの説明をそのまま信じず、元の依頼、実際の差分、AGENTS.md、QUALITY_POLICY.md、関連テストを照合してください。今回の役割は読み取り専用レビューです。

確認内容：
- 本来の課題が再現でき、修正が受け入れ条件を満たすか。
- 変更範囲逸脱、思い込み、誤ったテスト、見落とした状態遷移、未確認の画面品質がないか。
- PWAの320px幅、文字拡大、キーボード操作、動作軽減、エラー時の復帰。
- 認証・ユーザー分離・RLS・AI送信・プライバシー上の回帰。
- CIの対象head SHA、必須Verify、Vercel、競合、レビュー結果が最新か。

判定は「採用候補」「修正必要」「保留」のいずれかとし、根拠と未確認を明記してください。
自己申告の採点だけで品質向上やマージ可否を決めないでください。
```
